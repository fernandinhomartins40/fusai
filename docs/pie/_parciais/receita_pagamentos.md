# PIE · Motor C §5.2 — Proteção comercial e financeira (parcial)

Escopo: identidade → organização → saldo/limite → reserva → provedor → liquidação → contabilização → auditoria.
Método: leitura do código (commit `43dd2c3`). Nenhum teste foi executado: o banco de teste compartilhado estava em uso. Também não houve acesso à produção nem ao Asaas real.
Legenda: **CONFIRMADO** = comprovado pelo código (o caminho existe e foi lido linha a linha). **SUSPEITO** = depende de comportamento externo (provedor/Asaas) ou de execução ainda não feita.

## 1. Fluxo do dinheiro (diagrama textual)

```
ENTRADA DE DINHEIRO (Pix, Asaas — conta da fusai)
 Org (painel/MCP/v1 topups) ─► createOrgTopup ─► amountCents = base + ⌈base×fee%⌉ (servidor)
 Usuário final (v1/checkout/pix, session token ou secret) ─► createAppUserCheckout
        └─ preço/créditos = CreditPackage do PROJETO (definido pelo CLIENTE, sem vínculo preço↔crédito)
            │
            ▼  Asaas POST /payments (PIX) + /pixQrCode   →  Payment(PENDING, publicId chk_…)
 Webhook Asaas ─► POST /webhooks/asaas (token asaas-access-token, timingSafeEqual)
            └─ InboundWebhookEvent(eventKey UNIQUE) ─► fila BullMQ ─► processWebhookEvent
                 paid     → creditPayment: GET /payments/{id} no Asaas (status + valor == amountCents)
                            → UPDATE Payment WHERE creditedAt IS NULL → Ledger PURCHASE (+BONUS)
                 refunded → applyRefund: debita até o disponível; falta → SUSPENDE org + AuditLog
                 expired  → markExpired (PENDING → EXPIRED/CANCELED)
 Jobs: expire-payments (1 min, reconcilia com GET e cancela), sweep-webhooks (2 min)

CRÉDITOS SEM ENTRADA DE DINHEIRO (emissão)
 welcome_bonus (admin) · ajuste admin ADJUSTMENT · freeCreditMicros por AppUser novo (cliente)
 · ajuste BONUS de usuário final (cliente: painel + MCP agent) · bônus de pacote (cliente)
     └─ nenhum deles debita a carteira da organização  ◄── R-01

CONSUMO (gateway /v1/chat/completions)
 auth: secret key (hash+pepper) | session token JWT 15 min (appUser+project) | X-Fuse-User
  → resolveBilling: ORG_WALLET [org] | END_USER_WALLET [user] | HYBRID [user, org] | INTERNAL (sem reserva)
  → preço no servidor: priceModel (AUTO: ⌈custoUSD×câmbio×markup×1e6⌉ | FIXED)
  → hold = max(candidatos) ⌈prompt_est⌉×in + min(max_completion_tokens ?? max_tokens ?? 4096, maxOut)×out
  → spendLimit da chave: SUM(UsageLog do mês) + hold ≤ limite (leitura não atômica) ◄── R-04/R-05
  → reserve: UPDATE Wallet SET reserved+=hold WHERE balance-reserved+limit ≥ hold (+ WalletHold TTL 15 min)
  → provedor (corpo do cliente repassado; max_tokens NÃO é imposto) ◄── R-02
  → finishRequest/settle (1 transação): DELETE hold, reserved-=hold, SELECT … FOR UPDATE,
        cobra min(custo_real, disponível) → Ledger USAGE (UNIQUE por requestId) + UsageLog
        diferença = "absorbed" (prejuízo da fusai, errorCode charge_capped)
  → release-holds (5 min): reservas vencidas voltam
SAÍDA PARA O CLIENTE: OutboundWebhook (outbox na mesma transação) assinado HMAC t.body, 6 tentativas
```

## 3. Controles verificados como corretos

- **Reserva atômica** (`wallet.ts:84-89`): um único `UPDATE … WHERE balance - reserved + limit ≥ hold`. A CHECK `reservedMicros ≥ 0` e `WalletHold.amount ≥ 0` vêm da migração `20261014161000_wallet_checks`.
- **Liquidação idempotente**: `DELETE … RETURNING` do hold, `UNIQUE(type, referenceType, referenceId)` no ledger, P2002 tratado como duplicata. Hold de outra carteira provoca erro. Ledger e saldo se atualizam na mesma linha (`UPDATE … RETURNING balanceAfter`).
- **Saldo pré-pago nunca negativo** (D-128): o `settle` faz `SELECT … FOR UPDATE` e limita a cobrança ao disponível. O refund debita até zero, e o estorno pelo admin é recusado se os créditos já foram usados.
- **Reservas órfãs**: `releaseExpiredHolds` (CTE `DELETE … RETURNING` + `UPDATE` agregado) roda a cada 5 min e no início do worker.
- **Dinheiro**: tudo em `BigInt` micros e `Int` centavos. `costForTokens`, `mulDecimalsCeil` e `ceilDiv` arredondam para cima, sem float (`toCents` usa `Math.round(v*100)` só para comparar com o Asaas, aceitável). A taxa de recarga é `⌈base×pct/100⌉`.
- **Preço só no servidor**: o valor do Pix vem do pacote ou de `amountCents` validado (mínimo R$ 5,00 com `PIX_MIN_CENTS`, máximo R$ 10.000). O cliente não define o preço por token. `fuse/auto` só escolhe entre modelos `isServable` e permitidos ao projeto e à chave de teste, e o hold usa o pior caso entre os candidatos.
- **Webhook Asaas**: token comparado em tempo constante e com tamanho fixo (`ASAAS_WEBHOOK_TOKEN` min 8, bloqueado `change-me` em produção). `eventKey` UNIQUE. **Nunca credita confiando no corpo do webhook**: faz `getPayment` e confere status e valor (`amount_mismatch` não credita). O claim usa `creditedAt IS NULL`. Eventos fora de ordem (refund antes de paid, overdue depois de paid) são tratados.
- **Expiração**: o job reconcilia com o Asaas antes de expirar (credita se já pago) e cancela a cobrança remota.
- **Isolamento do usuário final**: o session token liga `sub` ao `pid` e é verificado contra o banco. Origin precisa estar em `allowedOrigins`. Secret key com Origin é recusada. `X-Fuse-User` só resolve dentro do projeto da chave. Checkout por session token só vê os próprios checkouts. Carteira de AppUser tem `creditLimit = 0`.
- **Organização suspensa** bloqueia o gateway. INTERNAL não reserva, mas grava o UsageLog.
- **Webhooks de saída**: outbox na mesma transação do crédito, HMAC `t.body`, lease anti-duplicidade, `redirect: manual`, `assertPublicUrl` (SSRF), retries 1m/5m/30m/2h/12h.
- **Auditoria**: ajustes com `actorId` e AuditLog; `payment.refund_shortfall` e `payment.refund_requested` são auditados; o admin vê `ledgerSum == balance` (`consistent`).
